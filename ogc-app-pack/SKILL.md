# OGC Application Package builder (MAAP)

Build an OGC Application Package: a container plus a CWL v1.2 document describing the
algorithm's inputs, outputs, image, and resource needs, so MAAP can run it as an OGC process.

The CWL is **never hand-written**. It is generated by `build_cwl_workflow.py` from
[`MAAP-Project/ogc-app-pack-generator`](https://github.com/MAAP-Project/ogc-app-pack-generator),
pinned at tag **1.1.0** — the same version the GitHub Action runs. Your job is to produce a correct
`algorithm_config.yml` and a container that honors the runtime contract below.

## The runtime contract — check this first, every time

These five rules are invisible in the config schema, and breaking any one of them produces a CWL
that validates cleanly and then fails at runtime. Verify them against the algorithm's actual source
before writing anything.

1. **Every input becomes `--<name> <value>`.** The generator binds each input as a flag whose prefix
   is the input's `name`. The algorithm's argument parser must accept exactly those flag names.
   `name: input_image` means the code must parse `--input_image`.
2. **The algorithm must write into `./output/` relative to its working directory.** The tool-level
   output globs `./output*` and returns it as a `Directory`. Anything written elsewhere is lost.
3. **Define exactly one output, `type: Directory`.** The generator hardcodes the tool output to a
   single `outputs_result` globbing `./output*`; a second output silently overwrites the first.
4. **`run_command` must be executable and resolvable** — either on `PATH` inside the image
   (the usual move: `COPY ... /usr/local/bin/x` + `RUN chmod +x`) or an absolute path.
5. **`Containerfile` `COPY` paths are relative to the repo root**, not the algorithm directory,
   because the Action builds with the repo root as context. Use `COPY ./my_algo/run.py ...`.

## Phases

### Phase 0 — Read the algorithm before asking anything

Never open the interview cold. Read the source, and if present the existing `algorithm_config.yml`,
`Containerfile`, and `cwl_workflows/`. From the code, infer: the input names and types, the output
filename and whether it lands in `output/`, the runtime (script / notebook / binary / existing
image), and dependencies. Then interview only to **confirm inferences and fill real gaps**.
State what you inferred and where you got it.

If the algorithm violates contract rules 1, 2, or 4, say so now and offer to fix the algorithm —
that is usually a smaller change than working around it in the config.

### Phase 1 — Interview

Read `references/interview.md`. It holds the full question inventory, the order to ask in, and the
explanation to give for each item. Rules:

- **Always explain why**, in OGC terms: what the answer becomes in the CWL, and what MAAP does with
  it. "I need `ram_min` because it becomes `ResourceRequirement.ramMin`, which is how MAAP sizes the
  job container — set too low, the platform may schedule a worker too small and the run gets killed."
- **Batch questions** with `AskUserQuestion`, grouped by theme (identity, inputs, resources,
  deployment, which files to keep), pre-filled with your inferred answer as the recommended option.
- **Don't ask what the repo already answers.** Author, license, and code repository come from git
  config, the `LICENSE` file, and `git remote`. Show them for confirmation, don't interrogate.
- Never invent an input the code doesn't parse, and never guess `ram_min`/`outdir_max` silently —
  a wrong `outdir_max` is a common, confusing runtime failure.

### Phase 2 — Scaffold

Write into the algorithm's directory. Templates are in `assets/`; pick the container pattern from
`references/containers.md` based on the runtime.

| File | Purpose | Write it? |
|---|---|---|
| `algorithm_config.yml` | The generator's input. Field reference: `references/algorithm-config.md` | **Ask** — see below |
| `Containerfile` | Builds the image. Patterns: `references/containers.md` | **Ask** — see below |
| `run.py` | Only for notebooks — the papermill shim mapping `--flags` to parameters | Notebooks only |
| `input.yml` | Sample CWL job file so the workflow can be test-run locally | **Ask** — see below |
| `.github/workflows/<algorithm-name>.yml` | Triggers the Action on push | **Ask** — recommended, see below |

**Four of these are the user's call — ask, batched with the Phase 1 questions.** Rounds 1, 6 and 7
of `references/interview.md` have the full framing; the short version:

- **`Containerfile` — write one, or point at a pre-built image?** Exactly one of the two is
  required: `validate_inputs.py` aborts with `algorithm_container_url or dockerfile-path must be
  provided` when neither is set, and rejects both at once. Writing one is the default. If the user
  wants a pre-built image instead, **ask which one** and set `algorithm_container_url` to it — then
  write no Containerfile and omit `dockerfile-path` from the Action. MAAP's own catalog and the trap
  that comes with it are in `references/containers.md` Pattern D; read it before offering the choice.
- **`algorithm_config.yml` — keep it in the algorithm directory?** It is always needed to *generate*
  the CWL, never to *run* one. Keeping it is what makes the package regenerable: bumping `ram_min`,
  adding an input, or re-registering after a code change is an edit-and-regenerate with it, and a
  hand-reconstruction from the CWL without it. Recommend keeping. Don't ask at all if they chose the
  GitHub Action — it reads `algorithm-configuration-path` on every push, so the config is mandatory
  there. If they decline, write it to the scratchpad and generate from there (see Phase 3).
- **`input.yml` — write a sample job file?** Purely local-testing convenience: it makes the test-run
  `cwltool <cwl> input.yml` instead of retyping `--text ... --output_file ...`. Nothing on MAAP reads
  it and the Action never touches it. Recommend it whenever a local test-run is plausible; if they
  decline, test-run with inline flags.
- **`.github/workflows/<algorithm-name>.yml` — set up the GitHub Action? (Recommend yes.)** Explain
  what it turns on before they agree: from then on, **every push to the branch it watches that
  touches the algorithm's files automatically rebuilds the image, pushes it to GHCR, regenerates and
  commits the CWL, and re-registers the process with MAAP** — no manual step, and no separate
  approval each time. That is why it is recommended (it is the supported path, and the only one that
  stamps `s:commitHash` with the commit being built) and also what to be deliberate about: each
  merge overwrites the live process of that name, since registration is an upsert. Ask **which
  branch** it should watch, and keep `algorithm_version` equal to it. If they say yes, walk them
  through getting a token from the profile page of the environment they are deploying to
  (<https://console.maap-project.org/profile/tokens> for production,
  <https://console.uat.maap-project.org/profile/tokens> for UAT) and adding it as the repository
  secret `MAAP_TOKEN` — the Action cannot register without it, and that walkthrough belongs to this
  path only; a local-only user sets `$MAAP_TOKEN` in their shell instead. Round 6 of
  `references/interview.md` has the full framing, the steps, and the links.

### Phase 3 — Generate the CWL

```bash
~/.claude/skills/ogc-app-pack/scripts/fetch_generator.sh          # clone 1.1.0 + venv, cached
~/.claude/skills/ogc-app-pack/scripts/generate_cwl.py \
    --config-file my_algo/algorithm_config.yml \
    --cwl-workflow-dir my_algo/cwl_workflows
```

`generate_cwl.py` reproduces the Action's environment derivation (`CWL_WORKFLOW_FILE_NAME`,
`DOCKER_TAG`, `GIT_COMMIT_HASH` from the local git repo) and then calls the generator's own
`build_cwl_workflow.py`, so the local output matches what CI will commit.

It derives branch, owner, and commit from the git repo **containing the config file**, so a config
kept outside the repo (the scratchpad, when the user declined to keep it) needs them passed
explicitly — otherwise it exits with `Could not determine the branch name`:

```bash
generate_cwl.py --config-file /tmp/.../algorithm_config.yml \
    --cwl-workflow-dir my_algo/cwl_workflows \
    --branch main --owner <gh-owner> --commit "$(git rev-parse HEAD)"
```
 Never edit the generated
CWL by hand — change `algorithm_config.yml` and regenerate, or the next push will revert you.

### Phase 4 — Validate and test-run

```bash
~/.claude/skills/ogc-app-pack/scripts/validate_cwl.sh my_algo/cwl_workflows/process_<name>_<branch>.cwl
```

Runs `cwltool --validate --strict` and `ap-validator --detail all`, the same two gates as the Action.
Both are static — they need no container engine, so always run them.

Then **build and test-run if a container engine is already installed**, and only then:

```bash
command -v docker || command -v podman     # detect; never install one
```

- **Engine present, Containerfile written** — build with the derived tag so it matches `dockerPull`
  in the generated CWL, then run. Build context is the repo root:
  ```bash
  TAG=$(scripts/generate_cwl.py --config-file my_algo/algorithm_config.yml --print-docker-tag)
  docker build -f my_algo/Containerfile -t "$TAG" .
  cwltool my_algo/cwl_workflows/process_<name>_<branch>.cwl my_algo/input.yml
  ```
  With podman, `podman build` and `cwltool --podman`.
- **Engine present, pre-built image** — nothing to build; `cwltool` pulls `algorithm_container_url`.
  A private registry needs a prior login, and MAAP's `mas.maap-project.org` images may not be
  pullable from outside the platform. If the pull fails, say so rather than working around it.
- **No engine** — stop after the validators. Report that the CWL is validated but untested, and name
  what is unverified: that `run_command` resolves, that the flags match the arg parser, and that
  results land in `./output/`. **Do not install Docker or Podman**, and do not offer to.

Failure decoding and the OGC requirement IDs are in `references/validate-and-run.md`.

### Phase 5 — Review, commit, push

Everything so far is local. **Show the user what was written, then prompt them to commit and push
it** — this is a review gate, not a formality, and it is also the precondition for registering:
MAAP fetches the CWL from a URL server-side, so an unpushed CWL is a 404 no matter what else is
right.

```bash
git status --short
git diff --stat          # and the CWL itself, if they want to see it
```

Walk through what each new file is and why it exists, then ask. The commit normally holds the
algorithm source, `algorithm_config.yml`, the `Containerfile`, `input.yml`, the generated
`cwl_workflows/*.cwl`, the Action workflow, and a `LICENSE` if you added one.

Rules for this phase:

- **Ask before committing, and ask again before pushing.** A push is outward-facing and, unlike a
  local commit, not yours to take back.
- **Check nothing secret is staged** — a token file, a `.env`, credentials in the config. Never
  commit a MAAP token.
- **A push can register the algorithm by itself.** If `.github/workflows/<name>.yml` is wired with
  `deploy-app-pack: true` and the push lands on a branch it watches, the Action builds the image,
  pushes to GHCR, commits the CWL back, and registers the process. Say this *before* they push, name
  the endpoint that workflow points at, and then do not ask the Phase 6 question as if nothing
  happened — point them at the Action run instead.
- **Commit order affects `s:commitHash`.** The generator stamps it from `HEAD` at generation time,
  so a CWL generated before its own algorithm was committed names the *parent* commit. For accurate
  provenance: commit the source and config first, regenerate the CWL, then commit the CWL. The
  Action sidesteps this — it generates after checking out the pushed commit.

After the push, get the SHA for the raw CWL URL that registration needs:

```bash
git rev-parse HEAD
```

### Phase 6 — Offer to register

**Once the changes are pushed, ask whether to submit the algorithm for registration.** Ask once,
here — even if they said earlier they only wanted a local build, because that answer was about how
far to go *before* seeing it work. If they decline at this gate, don't ask again. Skip the question
entirely if the push already triggered a registering Action; report that run instead.

Registration is an **upsert**: POST, and on HTTP 409 re-submit as `PUT /<processID>`, overwriting
whatever is deployed under this `algorithm_name`. It is outward-facing, so it happens only on an
explicit yes.

**Check two preconditions first** — MAAP fetches the CWL server-side and pulls the image itself:

1. The CWL is committed, pushed (Phase 5), and its raw URL resolves **anonymously** (pin it to the
   SHA from that push). An unpushed CWL is a 404 and registration cannot work.
2. `dockerPull` names an image MAAP can pull — pushed to GHCR and made **public** (new GHCR packages
   are private), built for `linux/amd64`.

If either is unmet, say which and offer the fix instead of the registration.

**Resolving the token**, in order:

1. Use `$MAAP_TOKEN` if set and non-empty — test it with `[ -n "${MAAP_TOKEN:-}" ]`, never echo it.
2. If unset or empty, **ask the user for their token**. Offer the safer route first: they run
   `! printf '%s' '<token>' > ~/.maap_token && chmod 600 ~/.maap_token` themselves and you pass
   `--token-file`. Say plainly that a token pasted into chat is in the transcript.
3. If they paste it anyway, write it to the **scratchpad** at mode 600, pass `--token-file`, and
   delete it afterwards. Never put a token in the repo, `algorithm_config.yml`, the CWL, a commit
   message, or memory, and never echo it or place it in a command whose output you print.

**Register:**

```bash
~/.claude/skills/ogc-app-pack/scripts/register_app_pack.sh \
    --cwl-url "https://raw.githubusercontent.com/<org>/<repo>/<sha>/my_algo/cwl_workflows/process_<name>_<branch>.cwl" \
    --endpoint https://api.maap-project.org/api/ogc/processes \
    --dry-run      # drop --dry-run to actually submit
```

It verifies the URL is anonymously reachable, sends the `proxy-ticket` request, follows the 409 → PUT
upsert, and prints `processPipelineLink` for watching deployment. The token reaches curl through a
mode-600 config file, so it never enters argv or shell history. **Do a `--dry-run` first and show the
user what will be submitted.**

| Environment | Register endpoint | Token from |
|---|---|---|
| Production | `https://api.maap-project.org/api/ogc/processes` (script default) | <https://console.maap-project.org/profile/tokens> |
| UAT | `https://api.uat.maap-project.org/api/ogc/processes` | <https://console.uat.maap-project.org/profile/tokens> |
| DIT | `https://api.dit.maap-project.org/api/ogc/processes` | The DIT console's profile page — ask, don't guess |

Take the token from the same row as the endpoint. A token issued by one environment 401s against
another, which is the usual reason a run that built cleanly dies at the register step.

Building and pushing the image is the other half of this phase; `references/deploy.md` has the GHCR
push and the `--platform linux/amd64` requirement. **Confirm before pushing an image too.**

Prefer letting the GitHub Action do all of it on push — it is the supported path and commits the CWL
back with the right commit hash. Register by hand when the user asks, or when there is no Action.
